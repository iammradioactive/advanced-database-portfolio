# Portfolio 2 - Query Processing and Optimisation

```bash
python portfolio-2-query-optimisation/benchmark.py
```

The script first removes only its three `opt_` indexes, keeping all integrity indexes.
It executes the three baseline queries, isolates the date rewrite, creates the indexes,
runs ANALYZE and repeats the queries. `EXPLAIN QUERY PLAN` and the full virtual-machine
`EXPLAIN` output are saved from the actual connection. Six business questions are
executed: customer order history, daily order mix, the dispatch queue, category revenue,
customer spending rank and dispatch exceptions. The latter queries demonstrate joins,
aggregation, a CTE/window function and an anti-join respectively.

## Measured comparison

The current results are in [results/SUMMARY.md](results/SUMMARY.md), generated by
`finish_assessment.py`. The benchmark saves all raw samples, native plans, CSV result
sets, index sizes and before/after equality checks. No timing is hard-coded here.

Each variant uses three warm-ups and eleven measured executions. Timings cover
`execute` and complete `fetchall` with `perf_counter_ns`. These are warm-cache local
measurements, not a production SLA. Very short indexed queries can produce large
speed-up ratios; inspect absolute milliseconds, spread and index costs too.

## Why each plan changed

Q1's customer/date covering index replaces the full orders scan and temporary sorting
with a selective lookup already ordered for LIMIT 20. Q2 rewrites `date(created_at)`
to a half-open UTC range over canonical timestamps, permitting a range search on the
created-at/status index. The GROUP BY can still require a temporary B-tree. Q3 uses a
small partial index containing only PAID orders in dispatch order, avoiding a table
scan and sorting of the whole relation. A SCAN of this small ordered partial index is
not equivalent to a scan of all 120,000 orders; read the full plan detail.

The Q2 ablation compares the original query, rewrite-only, index-only and combined
variants. Their actual timings and identical-result checks are in the run summary.

An index does not automatically make `date(created_at)` searchable by a raw timestamp
range. The index-only variant can scan a smaller covering index but still inspect many
entries. `results/plans/` preserves the exact observed behaviour; no planner choice is
forced with INDEXED BY. SQLite's EQP describes strategy, not per-operator execution
statistics, so the separately measured timings must not be called EXPLAIN ANALYZE.

## Costs and limitations

Index sizes, allocated database pages and index-build time are measured on each run
and recorded in `results/benchmark_summary.json` and `results/SUMMARY.md`.
Index maintenance adds work on writes, but this experiment does not quantify a
write-throughput regression. Results use one generated distribution and fixed query
parameters; wider selectivity, cold I/O, contention and repeated end-to-end workload
trials remain useful production evaluations. Re-running overwrites the evidence with
new actual measurements rather than preserving these values artificially.
